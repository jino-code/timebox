# ADR

## 設計思想

1. ユーザーが意図した操作だけをシステムに反映する。
システムが自動で判断・操作することで、利便性を上げるアプローチは採用しない。
ユーザーが選択・確定した操作だけが反映される設計を意識する。

2. スマホでの誤操作が起きにくい操作設計を優先する。
通勤電車や移動中など、スマホでタスクを管理することも多いので、スマホでも誤操作しにくい設計にする。

3. MVPファーストを重視しつつも、拡張しやすい設計を意識する。
コア機能の早期実装を優先してスコープを絞るが、将来の仕様追加や変更を見据えた設計を意識する。

## 技術選定

### ADR-001: フロントエンド / バックエンド

#### 決定
Next.jsを採用する。

#### 理由
- TypeScriptでフロントエンドとバックエンドを統一することで、コンテキストスイッチを減らしアプリケーションロジックの実装に集中するため。
- Server ComponentsとServer Actionsにより、フロントエンドとバックエンドを1プロジェクトで完結させて、CORSエラーなどの設定コストを削減するため。

#### 却下した選択肢
- Rails・Spring・Laravelなどのバックエンドフレームワーク
  - フロントエンドに別の技術スタックが必要になるため。

### ADR-002: DB

#### 決定
Supabaseを採用する。

#### 理由
- 認証を外部サービスに任せることで、実装漏れや実装ミスによるセキュリティリスクを下げ、パスワードのハッシュ化・セッション管理・CSRF対策などの実装コストを下げるため。
- RLSによってDB側でアクセス制御を完結させることでAPIの認可ロジックを削減できるため。

#### 却下した選択肢
- Firebase
  - RLSによるSQLベースのアクセス制御が使えないため。
  - NoSQLベースでリレーショナルなデータ構造や複雑なクエリに不向きであるため。

### ADR-003: テストフレームワーク

#### 決定
Vitestを採用する。

#### 理由
- TypeScriptとの親和性が高く、設定がほとんど不要であるため。
- ViteベースでJestと比較して、実行速度が速いため。

#### 却下した選択肢
- Jest:
  - Next.jsと組み合わせる際にBabelやSWRの設定が必要になるため。

### ADR-004: CI/CD

#### 決定
GitHub Actionsを採用する。

#### 理由
- マージのタイミングでテストを自動実行するなど、GitHub上のワークフローと自然に連携できるため。
- GitHubと統合されているため、別途CI/CDサービスの契約や設定が不要なため。

### ADR-005: インフラ

#### 決定
Vercelを採用する。

#### 理由
- Next.jsの開発元が提供しており、Next.jsとの親和性が高く設定コストが低いため。
- mainブランチへのマージで自動デプロイされ、CI/CDとの統合が容易であるため。

#### 却下した選択肢
- AWS
  - サーバーの設定やスケーリングの制御など、現時点では不要な機能が多いため。
  - 従量課金による想定外のコストが発生するリスクがあるため。

## アプリ設計

### ADR-001: タスク移動

#### 決定
2タップUIを採用する。

#### 理由
- 操作確定の瞬間が明確で、無駄に再レンダリングが発生しないため。

#### 却下した選択肢
- ドラッグ&ドロップ
  - 意図せず指を離してしまうことで、タスクの移動をやり直すストレスが発生すると考えたため。

### ADR-002: キャパシティ超過時のリスケジュール

#### 決定
ユーザが別の日時に移動させるか、インボックスに戻すかを選択する方式を採用する。

#### 理由
- ユーザー自身に選択させることで、時間コントロールの主導権をユーザに持たせるため。

#### 却下した選択肢
- 自動リスケジュール
  - システムが勝手に別日へ移動させると、タスクの行方が直感的に分かりづらくなると考えるため。

### ADR-003: Cascadingアルゴリズム

#### 決定
「〇時以降を押し出す」という明示的な操作によって、タスクを押し出す方式を採用する。

#### 理由
- ユーザーが時間コントロールの主導権を保持できるようにするため。

#### 却下した選択肢
- タスク移動時の自動押し出し
  - ユーザーの意図しない連鎖を招き、再構築にコストをかける可能性があるため。

## DB設計

### ADR-001: Tasksテーブルの開始時刻カラムの構成

#### 決定
Tasksテーブルの開始時刻はstart_timeの1カラムにする。

#### 理由
- 現在の仕様ではユーザーが意図した時刻と実際の配置時刻がずれることがないため、2カラムに分ける必要がないため。

#### 却下した選択肢
- requested_start_timeとactual_start_timeの2カラム構成
  - 当初はタスク移動時に後続タスクが自動で押し出される仕様だったため、以下の2つの理由から開始時刻を2カラムに分けて持つ設計を検討していた。
    - ユーザーが希望した時刻（requested_start_time）を保持することで、前のタスクが削除された際に元の希望時刻に戻れるようにするため。
    - 計算済みの実際の時刻（actual_start_time）を保持することで、画面表示のたびに再計算する必要をなくしパフォーマンスを確保するため。
  - しかしCascadingを明示的な操作に変更したことで、希望時刻と実際の配置時刻がずれることがなくなり、2カラムに分ける理由がなくなったため却下した。
